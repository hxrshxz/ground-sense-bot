# 🧠 How Intent Classification Works - The Smart Architecture

## TL;DR - It's NOT Hardcoded, It's INTELLIGENT!

Your system uses a **2-layer architecture** that handles BOTH predefined intents AND open-ended questions:

```
User Query → Intent Layer → Dynamic SQL Layer → Visualization Layer
```

## 🎯 Layer 1: Intent Classification (Smart Router)

### What It Does:

Categorizes queries into **semantic buckets** (not rigid rules):

```go
IntentSummary             // "show data for X", "summarize Y"
IntentTrend               // "trend", "over time", "historical"
IntentCompare             // "compare", "vs", "difference"
IntentTopRanking          // "top 10", "worst", "highest"
IntentCategoryDistribution // "distribution", "breakdown by category"
IntentMapCategory         // "show map", "visualize location"
IntentListBlocks          // "list blocks", "which blocks"
IntentRechargeBreakdown   // "recharge sources"
IntentExtractionBreakdown // "extraction by sector"
IntentUnknown             // ⭐ FALLBACK for anything else
```

### Why Intents Are Important:

1. **Performance**: Routes to optimized handlers (faster DB queries)
2. **Context**: Knows what entities to extract (locations, years, metrics)
3. **Visualization**: Suggests appropriate chart types
4. **Error Handling**: Provides specific error messages

### What Happens When Query Doesn't Match Any Intent?

**Answer: It STILL WORKS!** 👇

## 🚀 Layer 2: Dynamic SQL Generation (The Safety Net)

When intent = `UNKNOWN` or SQL needed, the system:

1. **Sends query to LOCAL LLM** (Ollama/SQLCoder running on your machine)
2. **LLM generates SQL** based on your database schema
3. **Executes the SQL** to get results
4. **LLM picks visualization** type based on data shape

### Example: Question Outside Intent List

**User asks**: "Which districts have rainfall above 600mm and stage below 80%?"

```
Step 1: Intent Detection
├─ Intent: UNKNOWN (no predefined handler)
├─ Entities: None specific
└─ Triggers: Dynamic SQL path ✅

Step 2: LLM SQL Generation
├─ Prompt sent to SQLCoder with schema
├─ Generated SQL:
   SELECT d.district_name, a.rainfall, a.stage
   FROM assessments_summary a
   JOIN blocks b ON a.block_uuid = b.block_uuid
   JOIN districts d ON b.district_uuid = d.district_uuid
   WHERE a.year = '2024-2025'
     AND a.rainfall > 600
     AND a.stage < 80
   GROUP BY d.district_name, a.rainfall, a.stage
   ORDER BY a.rainfall DESC;
└─ Executes SQL → Gets Results ✅

Step 3: Visualization Selection
├─ LLM sees: 15 rows, 3 columns (district, rainfall, stage)
├─ Suggests: "bar" chart (good for comparing districts)
└─ Frontend renders: Interactive bar chart ✅
```

**Result**: User gets exactly what they asked for, even though it wasn't a predefined intent!

## 📊 Layer 3: Visualization Layer (Flexible Templates)

Charts are NOT hardcoded to specific intents. Instead:

```typescript
// Backend sends chart TYPE, frontend has templates
Chart Types Available:
  - bar, line, area          // Basic charts
```

**Key Point**: LLM chooses chart type based on **data shape**, not intent!

### Example 2: Dynamic Query

**Query**: "Show me blocks where extraction increased by more than 20% compared to last year"

```
Intent: UNKNOWN (no predefined handler)
SQL Generated by LLM:
  WITH current AS (
    SELECT block_uuid, total_extraction
    FROM assessments_summary WHERE year = '2024-2025'
  ),
  previous AS (
    SELECT block_uuid, total_extraction
    FROM assessments_summary WHERE year = '2023-2024'
  )
  SELECT b.block_name,
         c.total_extraction as current,
         p.total_extraction as previous,
         ((c.total_extraction - p.total_extraction) / p.total_extraction * 100) as pct_change
  FROM current c
  JOIN previous p ON c.block_uuid = p.block_uuid
  JOIN blocks b ON c.block_uuid = b.block_uuid
  WHERE ((c.total_extraction - p.total_extraction) / p.total_extraction * 100) > 20
  ORDER BY pct_change DESC;

Chart: bar chart showing percentage changes
Speed: ~400ms (complex query, but works!)
```

### Example 3: Complex Analytics

## 🛡️ Why This Architecture is BRILLIANT

### 1. **Best of Both Worlds**

- Predefined intents = Fast, optimized queries
- Dynamic SQL = Handles anything else

### 2. **No Dead Ends**

- Every question gets answered
- If one layer fails, next layer catches it

### 3. **Scalable**

- Add new intent? Just add handler
- Don't need to update intents? LLM handles it

### 4. **Safe SQL Generation**

- LLM has EXACT schema (no hallucination)
- SQL validated before execution
- Results checked before visualization

### 5. **Smart Visualization**

- Chart type matches data shape
- Not locked to specific intents
- Adapts to result structure
